## 1. 조사 결과와 근거 수준

현재 읽을 수 있는 자료는 사용자 첨부 요청문, 이 포트폴리오의 콘텐츠·도식, 이전 포트폴리오입니다. 모두닥 원본 저장소와 개발 커밋은 아직 확보하지 못했습니다. 첨부에 언급된 현대오토에버 지원서 HTML 자체도 제공되지 않았으므로 제출 내용은 사용자가 전달한 서술을 기준으로 합니다.

‘일부 확인’은 경험 서술을 확인했으나 구현·기여를 소스로 검증하지 못했다는 뜻입니다. 현재 포트폴리오에 적힌 함수명이나 커밋 해시는 원본 증거가 아닙니다.

7. 관리자 검색·정렬·페이지네이션·승인·거절·숨김은 조사 후보입니다. 실제 담당 변경이 확인된 기능만 본문에 채택합니다.
8. 진료 데이터 이전은 환자 데이터 이전이라고 바꾸지 않습니다. 운영 데이터나 사용자 정보는 열람·복사하지 않아도 모델·코드·검증 기록으로 조사할 수 있습니다.

## 2. 페이지별 콘텐츠 초안

아래 문장은 사용자 제공 경험을 바탕으로 한 검토용 초안입니다. 실제 소스로 검증 완료했다는 의미가 아니며, 원본 조사 후 기여와 구현 범위에 맞춰 조정합니다. 검토 메모는 공개 화면에 넣지 않습니다.

### 01 · Overview

**제목:** 사용자 화면부터 데이터 구조까지, 운영 중인 의료 정보 서비스를 개선하다.

**소개:** Django·JavaScript·React Native 기반 의료 정보 플랫폼에서 웹·앱 기능과 백엔드 API 개선에 참여했습니다. 기존 구조를 분석하고 데이터 이전, 이미지 로딩, 운영 기능, 실험과 홈 개인화를 개선했습니다.

- **Problem:** 병원 탐색과 리뷰 경험을 개선하려면 사용자 화면뿐 아니라 기존 데이터·조회 구조도 함께 살펴야 했습니다.
- **Solution:** 웹·앱·관리자 기능과 연결된 Django 로직을 분석하고, 화면과 데이터 처리 흐름을 개선했습니다.
- **Result:** 데이터 구조, 이미지 로딩, 운영 기능과 사용자 탐색 흐름을 개선하는 작업에 참여했습니다.

**핵심 구현:** 진료 데이터 이전 / 이미지 조회·요청 시점 개선 / 관리자 업무 개선 / 실험·개인화.

**기술:** Django, JavaScript, React Native. DB·SDK 연결은 원본 대조 후 확정.

**시각화:** 왼쪽 Web·App·Admin 3개 진입점, 중앙 Django 담당 기능, 오른쪽 관계형 데이터 영역을 배치합니다. 실험·계측은 아래 별도 영역에 놓고 확인된 클라이언트와 연결합니다. 전체 서비스 구성과 본인 담당 영역을 구분합니다.

### 02 · DB Migration

**제목:** 분산된 진료 정보 구조를 재설계하고 20만 건 이상을 이전하다.

**소개:** 기존 모델의 참조 관계를 분석하며 진료 정보 변경 시 데이터가 불일치할 위험을 발견했습니다. 공통 진료 정보를 분리하고 관계를 재설계한 뒤 기존 데이터를 이전했습니다.

- **Problem:** 여러 모델에 분산된 진료 정보는 항목 추가·수정 시 일관되게 관리하기 어려웠습니다.
- **Solution:** 모델 관계를 재설계하고 Django 데이터 이전 로직을 작성했습니다. 백업 데이터로 두 차례 테스트하며 중복과 참조 관계를 검증했습니다.
- **Result:** 20만 건 이상의 데이터를 이전하고 운영 반영 후 새 모델과 기존 API의 동작을 확인했습니다.

**핵심 구현:** 기존 참조 분석 / 공통 정보 분리·관계 재설계 / 데이터 이전 / 백업 기반 2회 검증.

**기술·성과:** Django 모델·마이그레이션, 20만 건 이상 이전, 백업 기반 2회 테스트. 수치는 제공된 제출 경험 기준입니다. 데이터 이전과 주요 기능 확인을 전체 정합성의 완전한 보증으로 표현하지 않습니다.

**시각화:** Before/After를 가로로 비교하고 그 아래에 이전→중복·참조 검증→API 확인의 짧은 띠를 둡니다. 실제 ERD는 전후 모델과 FK 확인 후 작성하며, 현재 단계에서는 모델명·FK 방향·1:N 연결선을 확정하지 않습니다.

### 03 · Performance Optimization

**제목:** 조회 구조와 요청 시점을 바꿔 이미지 로딩을 약 9초에서 2초로 줄이다.

**소개:** 병원 상세 화면의 이미지 로딩 지연을 분석하고 Django 조회와 프론트엔드 요청 시점을 함께 개선했습니다. 화면에 필요한 데이터만 조회하고 상세 이미지는 모달 진입 시 요청하도록 조정했습니다.

- **Problem:** 분산된 이미지 데이터 조회와 초기 화면의 이미지 요청으로 병원 상세 로딩이 지연됐습니다.
- **Solution:** 조회 경로에 맞춰 UNION, 필드·건수 제한, Prefetch를 적용하고 모달 기반 On-Demand Loading을 도입했습니다.
- **Result:** 당시 제출 경험 기준으로 이미지 로딩 시간을 약 9초에서 2초로 단축했습니다.

**핵심 구현:** 요청·ORM 병목 분석 / 조회 데이터 축소 / 관계 조회 개선 / 모달 진입 시 이미지 요청.

**기술·성과:** Django ORM, UNION, Prefetch, On-Demand Loading. 약 9초→2초는 기존 제출 성과이며 재측정·LCP 결과가 아닙니다.

**시각화:** Before는 초기 진입의 조회·응답·이미지 표시 경로, After는 초기 화면과 모달 진입 경로를 분리합니다. 각 서버 경로에 확인된 최적화만 붙입니다. 9초→2초 카드에는 ‘당시 제출 경험 기준’을 간결하게 표시합니다.

### 04 · Admin Workflow

**제목:** 동적 필터링과 검수 흐름을 개선해 운영 데이터 처리를 지원하다.

**소개:** 관리자 화면에서 필요한 데이터를 찾고 처리하는 흐름을 개선했습니다. 입력한 조건이 Django 조회와 목록 표시로 이어지는 과정을 정리하고 검수 업무를 지원했습니다.

- **Problem:** 운영자가 처리 대상 데이터를 찾고 검수하는 과정에 개선이 필요했습니다.
- **Solution:** 관리자 동적 필터링과 데이터 처리 흐름을 개선했습니다.
- **Result:** 조건에 맞는 데이터 조회와 검수 처리를 지원했습니다.

**핵심 구현 후보:** 필터 조건 연동 / 목록 갱신 / 검수 처리 / 입력·수정 흐름. 원본에서 본인 변경이 확인된 항목만 채택합니다.

**기술:** Django. AJAX 여부와 관리 대상·상태 값은 원본 확인 후 반영합니다. 작업 시간 단축 수치는 사용하지 않습니다.

**시각화:** 관리자 조건 입력→조회 조건 적용→목록 갱신을 상단에 배치하고, 선택 항목 처리→목록 상태 반영을 하단 회귀 흐름으로 구성합니다. 실제 저장 방식과 상태 변경이 확인된 경우에만 해당 연결을 사용합니다.

### 05 · A/B Testing & Personalization

**제목:** 실험 가능한 UI와 탐색 문맥을 활용한 홈 화면을 구현하다.

**소개:** 실험군별 UI 분기와 사용자 행동 계측을 구현하고, 최근 조회 기록과 위치 정보를 활용해 홈 콘텐츠를 구성했습니다. 실험과 개인화는 각각의 데이터 흐름으로 설명합니다.

- **Problem:** 화면 개선을 실험·관찰할 구조와 사용자 탐색 문맥에 맞는 홈 구성이 필요했습니다.
- **Solution:** Hackle 실험 분기와 행동 계측을 적용하고 Redux 상태를 활용한 홈 콘텐츠 구성을 개선했습니다.
- **Result:** UI 비교를 위한 실험·계측과 최근 조회·위치 기반 홈 표시를 구현했습니다.

**핵심 구현:** 실험군 UI 분기 / 행동 이벤트 / 최근 조회 상태 / 위치 기반 콘텐츠.

**기술:** Hackle, Redux, React Native. 이벤트 SDK·속성·실제 실험 화면은 원본 확인 후 확정합니다. 전환율·유의성 성과는 표시하지 않습니다.

**시각화:** 위에는 실험 조회→A/B UI 분기→행동 이벤트, 아래에는 최근 조회·위치 입력→홈 콘텐츠 구성을 배치합니다. 개인화가 Hackle 할당 결과에서 직접 생성되는 것으로 그리지 않습니다. 이벤트 수집 시스템은 호출 코드에 맞춰 명명합니다.

### 06 · Feature Engineering

**제목:** 병원 탐색부터 리뷰까지, 웹·앱의 사용자 흐름을 개선하다.

**소개:** PC 병원·의사 상세 화면을 리팩토링하고 주변 병원 검색과 리뷰 기능을 개선했습니다. React Native 앱 홈·배너와 연결된 Django API도 수정했습니다.

- **Problem:** 병원 정보를 찾고 리뷰를 작성·확인하는 화면과 기능에 사용성 개선이 필요했습니다.
- **Solution:** 상세 화면, 주변 검색, 리뷰 업로드·조회와 앱 홈·배너를 개선했습니다.
- **Result:** 웹·앱에서 병원 탐색과 리뷰 이용 흐름을 개선했습니다.

**핵심 구현:** PC 상세 리팩토링 / 주변 병원 검색 / 리뷰 업로드·조회 / 앱 홈·배너.

**기술:** JavaScript, React Native, Django. 실제 파일과 담당 diff로 각 항목을 확인합니다.

**시각화:** 본인 변경을 확인할 수 있는 실제 화면 3~4개와 담당 구현 1~2줄을 배치합니다. 화면이 없다면 검증된 기능별 구현 요약 카드로 구성합니다. 가짜 서비스 화면은 만들지 않습니다.

## 3. 도식 확정을 위한 조사 순서

1. 원본 저장소 경로와 작성자 이름·메일을 확인합니다. 커밋 작성자와 변경 diff를 교차 검토하고, 기존 코드가 존재한다는 이유로 본인 기여로 귀속하지 않습니다.
2. Django 라우팅·view·모델과 웹/앱 호출부를 따라 기능별 파일·커밋·호출 흐름 표를 작성합니다.
3. 데이터 이전 커밋의 부모와 변경 이후 모델을 비교해 실제 FK·unique 제약·이전 매핑·검증 범위를 확인합니다. 스키마만으로 데이터 정합성을 보증하지 않습니다.
4. 이미지 요청 경로별 쿼리와 프론트 트리거를 따로 정리해 UNION·Prefetch·모달 호출의 관계를 확정합니다.
5. 관리자 요청·조회·저장, Hackle 할당·노출·이벤트, Redux 갱신·사용 위치를 확인합니다.
6. 공개용 도식은 확인된 구조를 업무 개념으로 추상화합니다. 회사 코드, 내부 엔드포인트, 운영 값과 사용자 정보는 싣지 않습니다.

원본 확보 전에는 이 문서를 기술 검증 완료 보고서나 실제 ERD로 사용하지 않습니다. 요청에 따라 UI 구현은 콘텐츠·도식 검토 후 진행합니다. 현재는 앱 코드를 변경하지 않아 TypeScript·ESLint·빌드·화면 검증은 실행하지 않았습니다.
